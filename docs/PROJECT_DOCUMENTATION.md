## 1. Architecture

    Browser: React 19 + Vite
       | HTTP /api requests with bearer token
       v
    Vite development proxy: 127.0.0.1:5173 -> 127.0.0.1:8000
       v
    FastAPI routes and middleware
       | request validation, authentication, role checks
       v
    SQLAlchemy models and queries
       | ODBC Driver 17, Windows authentication
       v
    SQL Server: B3A-S7-T4 on INBAAVVMMARSSQL,1433

The main request path is:

1. A person uses the React application at localhost:5173.
2. The frontend HTTP helper sends requests to /api. Vite proxies those requests to 127.0.0.1:8000 during local development.
3. FastAPI validates request data, checks the session and role, and calls SQLAlchemy.
4. SQLAlchemy reads or writes the dbo tables in SQL Server using the backend process’s Windows identity.
5. FastAPI returns JSON, except Excel export, which returns an xlsx response.

SSMS is the database client used to inspect/manage SQL Server; it is not the application database server. The backend must run on a computer that can reach SQL Server, including the company VPN when required.

## 3. SQL Server database and field mapping

### 3.1 Tables used by the application

The three business tables are dbo.Fines, dbo.Users, and dbo.ActivityEvents. The backend also maps two support tables present in the connected database: dbo.sessions and dbo.import_batches.

| Table | Purpose | Key behavior |
| --- | --- | --- |
| dbo.Fines | Fine, delivery, invoice, payment and validation records | fine_id is identity; row_version is SQL Server timestamp/rowversion generated by SQL Server |
| dbo.Users | User identity, requested/assigned roles, approval and active state | user_id is identity; email is unique; password hashes are not returned by APIs |
| dbo.ActivityEvents | Fine comments, validation decisions and audit events | event_id is identity; foreign keys link actor/fine/target where applicable |
| dbo.sessions | Hashed bearer-token key, user ID and expiry | Raw bearer token is not stored in SQL Server |
| dbo.import_batches | Workbook content digest for duplicate-file protection | Current import route is disabled, so this table is not written through the UI/API |

In SQL Server mode, FastAPI startup does not call create_all or run migrations. The backend assumes the mapped tables and columns already exist. The optional bootstrap.py is different: it calls Base.metadata.create_all and inserts an Admin. Do not run it against the existing company database unless that DDL/data write is explicitly intended and reviewed.

| --- | --- | --- |
| fine_id | fineId | Fine record identifier |
| customer_id | customerId | Customer identifier |
| customer_name | customerName | Customer display name |
| order_id | orderReference | Order reference |
| invoice_id | invoiceId | Invoice identifier |
| fine_date | fineDate | Fine date |
| fine_amount | fineAmount | Fine amount, decimal(18,2) |
| fine_reason | reasonCategory | Fine reason |
| root_cause_area | sourceArea | Logistics, Warehouse, Manufacturing, or Unknown |
| validation_status | status | Pending, Valid, or Invalid |
| ordered_qty | orderedQuantity | Ordered quantity |
| produced_qty | producedQuantity | Produced quantity |
| dispatched_qty | dispatchedQuantity | Dispatched quantity |
| delivered_qty | deliveredQuantity | Delivered quantity |
| promised_delivery_date | expectedDeliveryDate | Promised delivery date |
| actual_delivery_date | actualDeliveryDate | Actual delivery date |
| evidence_notes | reasonDescription | Evidence/request notes; Viewer request comment is stored here and in ActivityEvents |
| invoice_amount | invoiceAmount | Invoice amount, decimal(18,2) |
| payment_due_date | paymentDueDate | Payment due date |
| retailer_paid_at | retailerPaidAt | Retailer payment timestamp |
| payment_received_at | paymentReceivedAt | Payment received timestamp |
| amount_received | amountReceived | Amount received, decimal(18,2) |
| payment_verified_at | paymentVerifiedAt | Payment verification timestamp |
| finance_status | financeStatus | Unpaid, AwaitingVerification, Verified, or Disputed |
| updated_at | updatedAt | Last update timestamp |

The SQL schema has no currency column. API and UI amounts currently use USD; this is an application assumption, not a per-row database value.

The existing schema checks allowed statuses, reasons, source areas and finance states; positive fine/invoice amounts; nonnegative quantities and received amounts; received amount not exceeding invoice amount; payment-date chronology; and updated_at not earlier than fine_date. row_version is server-generated, so backend inserts must omit it.

### 3.3 dbo.Users

| SQL column | Application meaning |
| --- | --- |
| user_id | User ID |
| full_name, email | Identity/profile fields |
| password_hash | Argon2 hash; never returned in API responses |
| requested_role | Requested role, stored as User or SuperUser |
| role | Assigned role: Admin, User, or SuperUser |
| approval_status | Pending, Approved, or Rejected |
| is_active | Additional SQL Server sign-in gate |
| reviewed_by_user_id, reviewed_at, review_comment | Admin account-approval metadata |
| created_at, updated_at | Account timestamps |

Role conversion at the API boundary is User ↔ Viewer and SuperUser ↔ Super User. The UI displays Viewer as User. Admin is not selectable during public signup; Admin must be provisioned separately.

### 3.4 dbo.ActivityEvents

| SQL column | Application meaning |
| --- | --- |
| event_id | Event ID |
| fine_id | Related fine; null only for user-management events |
| target_user_id | Related user for user-management events; null for fine events |
| actor_user_id | User who caused the event |
| event_type | Validation, Finance, Comment, DataEdit, or UserManagement |
| field_name, old_value, new_value | Field/change description where required by event type |
| comment | Required, nonblank audit comment |
| created_at | Event timestamp |

The database enforces event-specific shapes. For a Comment event, field_name, old_value, and new_value must be null; fine_id is populated and target_user_id is null. A Viewer fine request stores its text in comment. A fine decision uses a Validation event with field_name=validation_status, old/new statuses, and the Super User’s comment. These constraints define how the backend must write events.

### 3.5 SQL Server access and data ownership

backend/database.py reads backend/.env. With Windows authentication, SQL Server sees the Windows identity of the Python process. That identity needs VPN/network access and SQL permissions for the operations used by the API. No SQL credentials are sent to the browser.

The application can insert fine requests, update validation status, add audit events, create/revoke sessions, and update account-approval fields. Automatic refresh is read-only. Normal SQL Server startup does not execute DDL.

## 4. End-to-end workflows

### 4.1 Sign-in and account approval

1. The sign-in page accepts a work email. It does not offer role buttons; the server returns the role already assigned to that account.
2. POST /api/auth/signin checks configured login mode, account approval state, active flag and optional requested-role match.
3. For an approved account, the backend generates a random bearer token, stores only its SHA-256 digest in dbo.sessions, and returns the raw token once. Sessions expire after eight hours.
4. The frontend saves the token in sessionStorage and sends it as Authorization: Bearer ... on authenticated requests.
5. Signup creates a pending dbo.Users row. An Admin approves or rejects it through User Management. A pending/rejected account cannot sign in.
6. Sign-out calls the logout API, deletes the server-side session, and clears sessionStorage.

Passwordless sign-in is controlled by ALLOW_PASSWORDLESS_LOGIN. The checked-in backend/.env.example defaults it to false; the local email-only UI requires the local backend/.env to set it to true. When enabled, knowing an active account email (or a database user ID through the API) is enough to sign in. Use this only for a controlled local demonstration, not internet-facing deployment. If signup omits a password, the backend hashes a random secret to satisfy the non-null database column; the user is not given that secret.

### 4.2 Viewer fine request and Super User review

1. A Viewer opens Fines Details and selects Submit Fine Request.
2. The form requires customer ID, fine date, positive amount, operational area, reason and a nonblank comment. Customer name/order reference are optional.
3. POST /api/fines inserts the new fine in dbo.Fines with status Pending. It generates order/invoice references when absent, sets invoice amount equal to the requested amount, and starts finance state as Unpaid with zero received.
4. The same transaction writes the Viewer’s request comment to dbo.ActivityEvents and evidence_notes.
5. A Super User sees the row in Fines Details with Review, reads the request comment, and can approve (Valid) or reject (Invalid) with a required comment.
6. The backend checks that the current status is still Pending and the submitted expected status/version match the SQL record. It updates the fine and records a Validation event. A stale request returns HTTP 409.
7. Closing the review dialog without saving leaves the row Pending. A final Valid/Invalid row cannot be reviewed again through this workflow.

Admin can inspect dashboard/activity data but the current review API intentionally allows only Super User decisions.

### 4.3 Admin account management

Admin views accounts in User Management, assigns Viewer or Super User to a pending signup, and approves or rejects it. The API writes approval status, role, active state, reviewer ID/time, review comment and update time to dbo.Users. Account decisions are separate from fine statement reviews.

### 4.4 Dashboard and activity

Dashboard fine KPIs/charts are derived from current fine records and shared applied fine filters. Admin/Super User also receive an unfiltered SQL summary for access/activity overview; supplemental account/activity totals are not scoped by fine filters. Activity Log reads paged dbo.ActivityEvents joined to actor/target names in dbo.Users.

## 5. Backend and middleware

### 5.1 Runtime components

- FastAPI defines routes, OpenAPI docs and dependency injection.
- Pydantic validates request bodies, query values, lengths, literal roles/statuses and dates.
- CORSMiddleware allows configured FRONTEND_ORIGIN (comma-separated origins), GET/POST/PATCH, and Authorization/Content-Type headers.
- Vite proxy is used locally; direct cross-origin hosting needs matching CORS configuration.
- current() extracts a bearer token, hashes it with SHA-256, reads the SQL session, checks expiry/account approval/active state, and returns the user.
- admin(), super_user(), activity_viewer(), and exporter() layer role checks over current().
- get_db() creates one SQLAlchemy session per request and closes it afterward.
- SQL Server mode maps existing dbo tables; it does not create them at startup.

### 5.2 Role permissions

| Capability | User (Viewer) | Super User | Admin |
| --- | :---: | :---: | :---: |
| Read dashboard and fine records | Yes | Yes | Yes |
| Apply fine filters and see filtered outputs | Yes | Yes | Yes |
| Submit fine request through UI | Yes | No UI form | No |
| Create fine via API | Yes, forced Pending + comment | Yes | No |
| Review Pending fine | No | Yes | No |
| Read Activity Log | No | Yes | Yes |
| Export fine records | No | Yes | Yes |
| Read/approve user registrations | No | No | Yes |
| Import Dataset | No | No | No; import dependency is disabled |

Frontend permissions control navigation and button visibility. Backend dependencies independently enforce access; hiding a button is not the security boundary.

### 5.3 SQL Server versus local/test scaffolding

database.py requires SQL Server configuration: DATABASE_URL with an mssql scheme, or DB_SERVER and DB_NAME. The active local project should use SQL Server. SQLite seed/test files are not used by normal local startup. seed_sample_data.py explicitly exits if connected to a non-SQLite engine. Do not run seed/bootstrap utilities against the company database without reviewing their write/DDL behavior.

## 6. Frontend state, filters, and live updates

### 6.1 Navigation and shared filters

Routes are hash-based: #dashboard, #fines, #activity, #users, and #import. Role permissions determine whether each route can render.

Fine filter state lives in App.jsx above Dashboard and Fines Details. Each page has local draft inputs; Apply copies drafts into shared applied state. The same fine filters drive dashboard charts/KPIs and fine rows. In-app navigation preserves filters and both views recompute from the same record snapshot. Clear all clears shared fine filters and activity filters. A full browser reload recreates React state and returns to default filters.

Activity Log has its own event-type and fine-ID filter state in App. User Management has no filter controls, so it has no Apply button.

### 6.2 Automatic updates

Manual Refresh buttons have been removed. The app polls SQL-backed endpoints every 30 seconds:

- Fine records are checked for all signed-in roles.
- Dashboard supplemental totals are checked for Admin/Super User.
- Activity Log refreshes its current server-paginated slice while open.
- User Management refreshes its account list while open.

Polling pauses when the browser tab is hidden and triggers a sync when the tab becomes visible. It retains the last successful snapshot if a poll fails. Applied filters are not cleared by polling; new fine data is filtered using the same state. This is polling, not a push/WebSocket connection, so an update can take up to about 30 seconds to appear.

### 6.3 Tables and charts

Fine sorting and pagination are client-side over the current fine dataset. Activity Log pagination uses API offset/limit. Fine table headers use shared sticky table styles. Charts use Recharts and respond to applied fine filters; selecting chart segments navigates to Fines Details with the corresponding filters applied.

Base path: /api. Except public health and auth bootstrap routes, protected requests require:

    Content-Type: application/json

Local OpenAPI/Swagger UI: http://127.0.0.1:8000/docs.

| Method + path | Authentication/role | Purpose |
| --- | --- | --- |
| GET /api/health | Public | API process health |
| GET /api/health/database | Admin | Run SELECT 1 against configured database |
| POST /api/auth/signup | Public | Create pending Viewer/Super User registration |
| POST /api/auth/signin | Public | Sign in and issue bearer token |
| GET /api/auth/me | Any signed-in role | Return current account profile |
| POST /api/auth/logout | Any signed-in role | Revoke current session |
| GET /api/users/requests | Admin | List account requests and approval states |
| POST /api/users/{user_id}/decision | Admin | Approve/reject account and assign role |
| GET /api/fines | Any signed-in role | Read/filter fine records |
| GET /api/dashboard | Any signed-in role | Table-derived totals; role-specific supplemental data |
| POST /api/fines | Viewer or Super User | Create fine; Viewer is forced to Pending + comment |
| GET /api/fines/{fine_id}/reviews | Any signed-in role | Read fine review/request-comment history |
| POST /api/fines/{fine_id}/reviews | Super User only | Approve/reject Pending fine with comment and concurrency check |

### 7.2 Authentication and accounts

POST /api/auth/signup body:

    {
      "fullName": "Example User",
      "email": "person@example.com",
      "requestedRole": "Viewer"
    }

requestedRole is Viewer or Super User and defaults to Viewer. password is optional; if supplied, it must be 8–128 characters. Returns HTTP 201 with pending status. Duplicate email returns 409.

POST /api/auth/signin: the frontend currently sends { "email": "person@example.com" }. The backend also accepts userId, optional password, and optional requestedRole. With passwordless mode enabled, email or database user ID identifies the account; otherwise email and password are required. The role comes from the approved SQL account. Success returns token and user (id, fullName, email, role).

GET /api/auth/me returns current profile. POST /api/auth/logout deletes the hashed session and returns signed-out status.

GET /api/users/requests returns identity, requested/assigned role, approval status and (in SQL Server mode) active/review timestamps and comment. It never returns password_hash.

POST /api/users/{user_id}/decision body:

    {"decision":"approve","assignedRole":"Super User"}

decision is approve or reject; assignedRole is Viewer or Super User. Only a pending account can be decided. Success returns saved status; an already-decided/missing account returns 409.

### 7.3 Fines, filters, dashboard

GET /api/fines accepts these optional query parameters:

| Parameter | Meaning |
| --- | --- |
| status | Pending, Valid, Invalid |
| customerId | Exact customer ID |
| sourceArea | Logistics, Warehouse, Manufacturing, Unknown |
| fromDate, toDate | Inclusive YYYY-MM-DD date bounds |
| reason | Exact fine reason |
| search | Up to 200 characters; searches fine ID, customer ID/name and order reference |

Reversed date ranges return 422. The response is an array of fine objects. SQL Server output uses the mapping in Section 3.2, plus version; where a Validation event exists it also includes latest review date/comment/reviewer. currencyCode is hardcoded to USD.

GET /api/dashboard has no query parameters. It returns fine totals, Pending count, fine deductions by area, finance status totals and outstanding values. Super User also receives ActivityEvents totals/recent events; Admin and Super User receive account totals. Fine filters are applied on the frontend to fine charts, not to this supplemental full-table summary.

POST /api/fines body example:

    {
      "customerId": "C001",
      "customerName": "Example Customer",
      "orderReference": "ORD-123",
      "fineDate": "2026-11-01",
      "fineAmount": 49.99,
      "sourceArea": "Logistics",
      "reasonCategory": "Damaged Goods",
      "requestComment": "Please review the supporting evidence."
    }

In SQL Server mode, customerId, fineDate, positive fineAmount, sourceArea and reasonCategory are required. customerName/orderReference are optional. Allowed reasons are the ten values in the Fines table constraint. For Viewer, requestComment is required and status is always Pending regardless of body status. The API returns the created fine with HTTP 201.

### 7.4 Fine review and Activity Log

GET /api/fines/{fine_id}/reviews returns history objects with reviewId, fineId, old/new status, reviewer ID/name, comment and timestamp. New fine-request comments appear as Request submitted history entries.

POST /api/fines/{fine_id}/reviews accepts a decision, nonblank comment, expected status and expected version:

    {
      "decision": "Invalid",
      "comment": "The delivery evidence does not support this deduction.",
      "expectedStatus": "Pending",
      "expectedVersion": 1
    }

The active UI offers Valid (Approve) or Invalid (Reject). A rejection reason is required. Only Pending records can be changed; closing the dialog without saving keeps the fine Pending. A stale expected status/version returns 409. Successful review returns the updated fine and writes a Validation ActivityEvent.

GET /api/activity-events query parameters:

| Parameter | Meaning |
| --- | --- |
| offset | Result offset; default 0, minimum 0 |
| limit | Page size; default 25, allowed 1–100 |
| eventType | Validation, Finance, Comment, DataEdit, UserManagement |
| fineId | Numeric fine ID |

Response shape:

    {"items":[],"total":0,"offset":0,"limit":25}

Each item includes event ID, fine/target user IDs and names, actor ID/name, event type, field, old/new values, comment and created timestamp.

### 7.5 Export and import

POST /api/exports/fines body:

    {"ids":["1001","1002"]}

Accepts 1–10,000 IDs. Admin and Super User only. IDs are de-duplicated; SQL Server IDs are parsed as integers; rows are reread from SQL Server. The response is an Excel file with the standard spreadsheet MIME type. The frontend sends all matching IDs, not only the visible table page.

POST /api/imports/validate exists in source, but importer() currently always raises 403. The Import Dataset page is not granted to any role, and the endpoint is not usable in the current application. Do not treat workbook imports as an available workflow.

### 7.6 Error handling

FastAPI errors use a JSON detail property. Common responses:

| Status | Typical meaning |
| --- | --- |
| 401 | Missing/invalid/expired token or invalid credentials |
| 403 | Not approved, inactive account, role denied, or import disabled |
| 404 | Fine does not exist |
| 409 | Duplicate email, already-decided account, stale review, or duplicate import digest if import is later enabled |
| 413 | Upload too large if import is later enabled |
| 422 | Invalid query/body, date range or unsupported fine reason |

When an authenticated request returns 401, the frontend clears the sessionStorage token and returns the user to sign-in.

## 8. Configuration and local run instructions

### 8.1 Prerequisites

- Windows with company VPN/network access required for SQL Server.
- Python and pip.
- Node.js/npm compatible with frontend/package.json (Node ^20.19.0 or >=22.12.0).
- Microsoft ODBC Driver 17 for SQL Server, or set DB_DRIVER to an installed compatible driver.
- A Windows account with the required database permissions.

### 8.2 Configure the backend

From the inner repository root (the folder containing backend and frontend):

    Copy-Item .\backend\.env.example .\backend\.env
    notepad .\backend\.env

The example contains these local settings:

    DB_AUTH=windows
    DB_SERVER=INBAAVVMMARSSQL,1433
    DB_NAME=B3A-S7-T4
    DB_DRIVER=ODBC Driver 17 for SQL Server
    DB_TRUST_CERTIFICATE=yes
    FRONTEND_ORIGIN=http://localhost:5173

backend/.env is ignored by Git; do not commit it. For the current email-only passwordless login UI, set ALLOW_PASSWORDLESS_LOGIN=true in the local backend .env. Keep passwordless mode in a controlled local demo only. The checked-in example defaults to false.

Install backend dependencies once:

    cd .\backend
    python -m pip install -r .\requirement.txt -r .\requirements-sqlserver.txt

Start the backend in its own PowerShell terminal:

    cd .\backend
    python -m uvicorn main:app --host 127.0.0.1 --port 8000

The backend should report that application startup completed and listen on http://127.0.0.1:8000.

### 8.3 Start the frontend

In a second PowerShell terminal, from the inner repository root:

    cd .\frontend
    npm.cmd ci
    npm.cmd run dev

npm.cmd avoids PowerShell’s npm.ps1 execution-policy issue. Open the URL printed by Vite, normally http://127.0.0.1:5173 or http://localhost:5173.

Useful URLs:

- Frontend: http://localhost:5173
- API health: http://127.0.0.1:8000/api/health
- Swagger/OpenAPI: http://127.0.0.1:8000/docs
- Database health: http://127.0.0.1:8000/api/health/database (Admin bearer token required)

Stop each server with Ctrl+C in its terminal. These commands run locally; they do not host the app on Vercel or expose it to the internet.

### 8.4 Build and quick checks

    cd .\frontend
    npm.cmd run build

The backend health route can be checked without login:

    Invoke-RestMethod http://127.0.0.1:8000/api/health

Database health requires an Admin bearer token. The UI also exercises the database through authenticated requests after sign-in.

## 9. Operational notes and known limits

1. **Passwordless login is not production authentication.** If enabled, possession of an active user email is enough to sign in through the current UI. Use only in a controlled local demonstration environment.
2. **No fine row ownership filter exists.** Approved roles with fine-read permission share the dataset; Viewer is not restricted to rows they created.
3. **Super User is the only fine reviewer.** Admin can monitor dashboard/activity but cannot approve/reject fines through the current review route.
4. **Import is disabled.** Import UI/API code exists, but the current backend role dependency rejects it.
5. **Automatic updates use polling.** Data checks run every 30 seconds; this is not instant server push or WebSocket. Making the browser tab visible triggers another check.
6. **Currency is assumed USD.** The existing Fines table has no currency column.
7. **Fine request creation writes SQL data.** It inserts into Fines and writes a request comment to ActivityEvents; this is an intentional workflow write, not a schema change.
8. **No schema migration system is included.** SQL Server DDL/table creation must be handled through the database owner’s process. Normal API startup will not repair mismatched tables.
9. backend/dashboard_profile.sql contains read-only aggregate SELECT statements. Run separately in SSMS if needed; the app does not call it.
10. Local logs and .env files are ignored by Git. Keep tokens, credentials and real customer information out of screenshots and commits.

## Appendix A: Constraints verified in SQL Server metadata

- dbo.Fines: allowed statuses, reasons, source areas and finance states; positive fine/invoice amounts; nonnegative quantities/received amount; received amount cannot exceed invoice amount; payment chronology; updated_at on/after fine_date; unique invoice ID; fine_id primary identity; row_version generated by SQL Server.
- dbo.Users: unique email; allowed role and approval status; requested role restricted to User/SuperUser; approval/review timestamps and active state constrained by approval state.
- dbo.ActivityEvents: allowed event types; nonblank comment; actor/fine/user foreign keys; fine-event target is null; field/old/new values constrained by event type.

This appendix describes connected database metadata inspected read-only. It does not perform or prescribe a SQL Server schema change.

### Additional notes for the disabled import handler

The current request is rejected by importer() before the dormant workbook code runs. If that guard is intentionally changed later, the handler expects an .xlsx workbook with exact headers CustomerID, Fines Imposed, Status, Reason, Date, and SourceArea; it caps upload size at 5 MB, expanded zip size at 50 MB, and data rows at 10,000. It validates the whole workbook before inserting and requires commit=true for writes. The digest check prevents repeat uploads of the same exact file. These are dormant source-code rules, not an available current workflow.

For the example DB_TRUST_CERTIFICATE=yes setting, ODBC encrypts the SQL connection but skips certificate identity validation. This setting is from the local example; use the organization’s approved certificate configuration in any shared/deployed environment.
